# MONIK — ОЧЕРЕДИ ЗАПРОСОВ К АГРЕГАТОРАМ

> Техническая документация реализации. Требования заданы
> `docs/architecture/05_RESOURCE_MANAGER.md` и
> `docs/architecture/12_RESOURCE_MANAGER.md`; этот файл их **не изменяет**
> и не заменяет (`CLAUDE.md` §43).

---

## 1. Зачем

Конфигурация всегда объявляла `requests_per_second` и
`max_concurrent_requests` для каждого провайдера, но эти значения не
доходили до Resource Manager: лимиты не регистрировались, и ограничения
частоты фактически не было. Level 1 отправлял примерно 17 запросов в
секунду на провайдера при настроенных ~5, получал HTTP 429, после чего
открывались circuit breaker'ы.

Теперь лимиты регистрируются при сборке приложения, и очередь провайдера
— это и есть механизм, который их применяет.

## 2. Схема

```
                       Resource Manager
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   Velora Queue           0x Queue            Uniswap Queue
   4.9 зап/с              4.9 зап/с            5.9 зап/с
        │                     │                     │
  ┌─────┴─────┐         ┌─────┴─────┐         ┌─────┴─────┐
  │ 1 Level2  │         │ 1 Level2  │         │ 1 Level2  │   ← раньше начатый
  │   ранний  │         │   ранний  │         │   ранний  │
  ├───────────┤         ├───────────┤         ├───────────┤
  │ 2 Level2  │         │ 2 Level2  │         │ 2 Level2  │   ← позже начатый
  │   поздний │         │   поздний │         │   поздний │
  ├───────────┤         ├───────────┤         ├───────────┤
  │ 3 L1 SELL │         │ 3 L1 SELL │         │ 3 L1 SELL │
  ├───────────┤         ├───────────┤         ├───────────┤
  │ 4 L1 BUY  │         │ 4 L1 BUY  │         │ 4 L1 BUY  │
  └───────────┘         └───────────┘         └───────────┘
        │                     │                     │
   одновременность       одновременность      одновременность
   rate limit            rate limit           rate limit
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
                   общий потолок запросов
                              │
                      circuit breaker
                              │
                     retry / backoff
                              │
                            HTTP
```

Порядок ступеней важен. Пауза по частоте выдерживается **до** захвата
общего потолка: запрос, ожидающий своей доли частоты, ничего не
выполняет. Если удерживать за ним место выполняющегося, общий потолок
превращается во второе ограничение частоты и удерживает каждого
агрегатора ниже настроенного значения — при потолке 32 и трёх
агрегаторах измеренная частота падала с 4.9/4.9/5.9 примерно до
3.3/3.7/4.0 запросов в секунду.

Telegram живёт **вне** этих очередей: у него собственный ресурс
(`telegram`) и собственный порядок — по времени формирования уведомления.
Очередь провайдера и очередь Telegram не блокируют друг друга.

## 3. Одна очередь на агрегатор

Очередь создаётся на область `provider_id` — без сети и операции. Это
означает, что **общий бюджет** делят:

- BUY и SELL;
- Level 1 и Level 2;
- котировки, комиссии и проверки доступности.

Так и должно быть: API ограничивает ключ целиком, поэтому создавать
отдельные независимые корзины для BUY и SELL нельзя — это дало бы вдвое
больше запросов, чем разрешено (`05_RESOURCE_MANAGER.md` §51).

Ошибка одного агрегатора не задевает остальных: очереди, лимиты и
circuit breaker'ы у них независимы (`05_RESOURCE_MANAGER.md` §48).

---

## 4. Приоритеты и порядок

Внутри очереди действует один ключ упорядочивания:

```
(приоритет, время начала работы, время создания запроса, sequence)
```

| Приоритет | Кто |
|---|---|
| 1 | Level 2, начатый раньше |
| 2 | Level 2, начатый позже |
| 3 | Level 1 SELL |
| 4 | Level 1 BUY |

Level 2 — один класс приоритета; «раньше» и «позже» различаются **вторым
элементом ключа**: временем начала проверки, а не временем создания
конкретного запроса. Без этого проверка, начатая позже, обгоняла бы
начатую раньше, стоило ей создать очередной запрос
(`05_RESOURCE_MANAGER.md` §17-18).

Внутри одного приоритета и одного времени начала действует FIFO по
времени создания запроса: `asyncio.gather` не определяет порядок
выполнения.

Прибыльность возможности на порядок **не влияет** (`04_SCHEDULER.md` §26).

## 5. Частота запросов

Единственный источник ограничения — `requests_per_second` из
конфигурации провайдера. Второго параметра для очереди нет.

Token bucket наполняется с этой скоростью. Запас (`burst`) не
настраивается отдельно и равен **одному** запросу.

Это не придирка, а условие соблюдения лимита. Корзина ёмкостью `B` при
частоте `R` способна выдать за секунду `B + R` запросов, поэтому запас
`floor(R)` превращал настроенные 5.9 запроса в секунду почти в двенадцать,
и Uniswap отвечал `429` при документированных шести. При `B = 1` в любое
секундное окно попадает не больше `ceil(R)` запросов. Средняя частота при
этом не меняется — исчезает только всплеск после простоя.

Поверх корзины действует **наименьшая пауза между запросами одной
очереди** — `resources.provider_min_interval_seconds`, по умолчанию
`0.1` секунды. Пауза поочерёдная: у каждого агрегатора собственная
корзина, поэтому запрос Velora не задерживает 0x. Telegram и RPC не
затрагиваются: им лимиты провайдеров не регистрируются.

Отдельному агрегатору пауза задаётся его собственным
`min_interval_seconds`; он заменяет общее значение **только для этой
очереди**. Требования у агрегаторов разные — один отвечает `429` там, где
другой работает без замечаний, — и замедлять из-за него остальных
незачем. Без этой настройки применяется общее значение.

```yaml
providers:
  - provider_id: zero_x
    requests_per_second: 4.9
    min_interval_seconds: 0.3   # только для 0x; у остальных остаётся общая
```

Действует то ограничение, которое строже: при частоте 4.9 запроса в
секунду шаг корзины равен 0.204 с, поэтому пауза 0.3 с становится
определяющей, а пауза меньше 0.204 с не изменила бы ничего.

Место в бюджете **резервируется**: запрос сразу списывает свою стоимость
и узнаёт, сколько ждать. Ожидающие не будят друг друга и не соревнуются
за одни и те же токены, поэтому порядок очереди сохраняется, а
погрешность вещественной арифметики не превращает ожидание в холостой
цикл.

Запрос дороже запаса выполнить невозможно — такой запрос отклоняется
явной ошибкой, а не ждёт вечно.

Измеренная нагрузка полного цикла (три агрегатора, 29 промежуточных
токенов, четыре суммы, BUY и SELL — 232 запроса на агрегатора):

| Агрегатор | Настроено | Лимит ключа | Длительность | Пик за секунду |
|---|---|---|---|---|
| 0x | 4.9 зап/с | 5 | 47.1 с | 5 |
| Velora | 4.9 зап/с | 5 | 47.1 с | 5 |
| Uniswap | 5.9 зап/с | 6 | 39.2 с | 6 |

Длительность равна `(запросы − 1) / частота`: быстрее настроенного
очередь не выдаёт, медленнее — тоже. Пик за секунду не выходит за
документированный лимит ключа.

## 6. Одновременность

Три независимых ограничения, каждое со своей задачей:

| Ограничение | Где | Что ограничивает |
|---|---|---|
| `scanner.level1.max_concurrent_requests` | Level 1 | сколько котировок цикл запрашивает одновременно |
| `scanner.level2.max_parallel` | Level 2 | сколько проверок выполняется одновременно |
| `providers[].max_concurrent_requests` | очередь провайдера | сколько запросов к этому агрегатору выполняется одновременно |
| `resources.global_max_concurrent_requests` | Resource Manager | общий потолок исходящих запросов |

Общий потолок считает только выполняющиеся запросы: ожидание своей доли
частоты в него не входит (см. §2).

Логическая одновременность задач и одновременность обращений к ресурсу —
разные величины (`05_RESOURCE_MANAGER.md` §21): двадцать проверок Level 2
могут существовать одновременно, обращаясь к провайдеру по два запроса.

## 7. Добавление нового агрегатора

Очередь появляется из конфигурации. Чтобы добавить агрегатор, нужно:

1. добавить его `provider_id` в доменный перечень провайдеров;
2. реализовать adapter по общему контракту;
3. зарегистрировать adapter в composition root;
4. описать провайдера в конфигурации:

```yaml
providers:
  - provider_id: new_aggregator
    enabled: true
    api_key: { env: "MONIK_NEW_AGGREGATOR_API_KEY" }
    supported_networks: [polygon]
    requests_per_second: 5.0
    max_concurrent_requests: 4
```

Очередь, лимит частоты, лимит одновременности и circuit breaker для него
создаются автоматически. Менять код очередей не требуется, ветвлений вида
`if provider == ...` в них нет (`CLAUDE.md` §7).

## 8. Circuit breaker

Порог отказов считается **логическими операциями**, а не попытками: три
повтора одного запроса — это одна попытка добиться результата, а не три
независимых отказа ресурса.

Отказом считается только недоступность. Ответы, описывающие запрос или
данные — отсутствие ликвидности, неподдерживаемая пара, некорректный
формат, — работоспособности провайдера не опровергают и счётчик отказов
не увеличивают.

То же правило действует в Health Monitoring: отказом доступности
считаются категории `network`, `timeout`, `rate_limit`, `provider` и
`authentication`. Отсутствие маршрута (`no_route`), ошибки данных и
валидации, неподдерживаемая операция и **наши собственные** ограничения
ресурса (`resource`, в том числе `resource_circuit_open`) состояние
провайдера не меняют: иначе один открывшийся breaker выдал бы подряд
десятки отказов и сам довёл бы агрегатора до `unavailable`.

Восстановление проходит полный цикл `CLOSED → OPEN → HALF_OPEN → CLOSED`.
`half_open_max_calls` ограничивает **одновременные** пробы; после
завершившейся пробы слот освобождается — при любом исходе, включая
ошибку, для которой счётчик отказов не ведётся. Иначе одна такая проба
занимала бы слот навсегда, и ресурс оставался бы в `HALF_OPEN` без
единого разрешённого запроса.

Разрешение выдаётся **непосредственно перед обращением** к ресурсу, одной
операцией с занятием слота. Проверка до постановки в очередь остаётся, но
только как быстрый отказ: между ней и выполнением проходят очередь и
пауза по частоте, и если считать её разрешением, то в `HALF_OPEN` его
получают все накопившиеся запросы разом.
