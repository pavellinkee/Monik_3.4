# MONIK — ПРОЕКТНАЯ ПАМЯТЬ

> **Назначение.** Переносимая память проекта Monik. Файл хранится в Git вместе с
> исходным кодом, поэтому переносится на другой VPS и в другое состояние Monik
> вместе с репозиторием.
>
> **Monik — одна программа.** `3.0`, `3.1`, `3.2`, `3.3` и имена каталогов и веток
> (`Monik_3.2`, `monik-3.3`) — технические обозначения состояний и релизов одной и
> той же программы, а не разные продукты. Правила и знания, записанные здесь и в
> `CLAUDE.md`, действуют для любого состояния Monik.
>
> **Правила ведения файла:**
> 1. Разделять **подтверждённые факты** и **гипотезы**. Каждый факт сопровождается
>    указанием, чем он подтверждён.
> 2. Не удалять полезную историю. Устаревшие записи переносить в раздел
>    «История изменений», а не стирать.
> 3. Обновлять раздел «Текущее состояние» при каждом значимом изменении.
> 4. Секреты (ключи API, Telegram-токены, содержимое `/etc/monik/monik.env`,
>    выгрузки production-базы) в этот файл не попадают никогда.
>
> **Порядок чтения при старте новой сессии:**
> `CLAUDE.md` → **этот файл** → `git log` → `docs/architecture/` → код.

## 1. Что такое Monik

Monik — сканер арбитражных возможностей на DEX-агрегаторах.

Двухуровневая схема (утверждена `docs/architecture/`):

- **Level 1** (`#V`) — массовое сканирование: BUY-котировки, определение MAX BUY,
  SELL, оценка комбинаций, порог прибыльности, создание `Opportunity`.
- **Level 2** (`#K`) — проверка найденной возможности по **тому же маршруту**
  свежими котировками с учётом комиссий и газа, расчёт net profit и статус
  подтверждения (`CONFIRMED` / `UNCONFIRMED` / `PARTIAL`).

Все внешние запросы идут через **Resource Manager** (очереди по агрегаторам,
приоритеты, rate limit, retry, circuit breaker). Source of truth восстанавливаемого
состояния — SQLite. Управление и уведомления — Telegram.

Агрегаторы, предусмотренные архитектурой: **1inch, 0x, Velora (ParaSwap), Uniswap**.
Сеть, которая реально использовалась: **Polygon**.

### `c5cec00` — что именно изменено

- `requests_per_second` и `max_concurrent_requests` из конфигурации **не доходили до
  Resource Manager**: `register_limits` вызывался только в тестах. Реальная нагрузка
  достигала ~17 запросов в секунду на агрегатора при настроенных ~5 — отсюда HTTP 429
  и массовые `resource_circuit_open`. Лимиты стали регистрироваться при сборке
  приложения, без ветвлений по имени агрегатора.
- BUY и SELL, Level 1 и Level 2 делят один бюджет провайдера (API ограничивает ключ
  целиком). Порядок обслуживания: Level 2 ранний → Level 2 поздний → Level 1 SELL →
  Level 1 BUY, внутри приоритета FIFO. Приоритет проверки Level 2 определяется
  временем её начала (поле `priority_at`).
- Пауза по частоте выдерживается **до** захвата общего потолка одновременности;
  rate limiter резервирует место вместо цикла «подождать и попробовать снова».
- Circuit breaker: завершившаяся проба в `HALF_OPEN` освобождает слот; отказом
  считается только недоступность; исчерпанный бюджет повторов одной логической
  операции — один отказ, а не три.
- Версия объявляется в одном месте (логи, диагностика, Telegram, `--version`).
- Telegram: меню с кнопками, подтверждение остановки и перезапуска, `/status` с
  версией, окружением, подсистемами и очередями, `/stats` из живого реестра метрик
  (раньше всегда возвращал нули).
- Резервное копирование: еженедельная задача (суббота, 03:00), `VACUUM INTO`,
  проверка целостности, ротация по числу копий, состояние видно в `/backup`.

### `f0cc242` — что именно изменено

- **0x `liquidityAvailable`.** Swap API v2 отвечает `200` и опускает `buyAmount`,
  `sellAmount`, `route` и `gas`, когда маршрута нет. Адаптер считал это повреждённым
  ответом. Добавлены категория ошибки `NO_ROUTE` и `NoRouteError`: повтора не вызывает,
  breaker не открывает, доступности провайдера не опровергает. При
  `liquidityAvailable=true` разбор остаётся строгим.
- **HTTP-заголовки.** Библиотека подставляла `accept: */*`, и Uniswap Trading API
  отвергал запрос. `Accept: application/json` задан в HTTP-клиенте — в единственном
  месте работы с HTTP, а не в каждом адаптере. Ответы `3xx` получили отдельный код
  `http_redirect_not_followed`.
- **Всплеск запросов.** Корзина ёмкостью `B` при частоте `R` выдавала за секунду
  `B + R` запросов: запас `floor(5.9) = 5` превращал настроенные 5.9 почти в 12 при
  документированном лимите ключа в 6. Запас снижен до одного запроса. Измеренный пик
  стал 5 / 5 / 6 вместо 8 / 8 / 10. Настроенные `requests_per_second` не менялись.
- **Пауза внутри очереди.** Добавлена `resources.provider_min_interval_seconds`
  (по умолчанию `0.1`) — наименьшая пауза между двумя запросами одной очереди
  агрегатора. Telegram и RPC не затрагиваются.
- **Circuit breaker.** Разрешение выдаётся непосредственно перед обращением к ресурсу,
  одной операцией с занятием слота пробы; слот освобождается при любом завершении
  пробы. Раньше в `HALF_OPEN` разрешение успевали получить все накопившиеся запросы.
- **Health Monitoring.** Отказом доступности считаются только категории `network`,
  `timeout`, `rate_limit`, `provider`, `authentication`. Отсутствие маршрута, ошибки
  данных и валидации, неподдерживаемая операция и собственные ограничения ресурса
  (включая `resource_circuit_open`) состояние провайдера не меняют. Пороги health не
  трогались — исправлена классификация.
- **Уведомление об остановке сканера.** Одно событие остановки — одно сообщение,
  через существующую систему операционных уведомлений; покрыты команда оператора,
  перезапуск, штатное завершение и критическая ошибка.
- **Диагностика.** В запись «quote request failed» добавлены `http_status` и пояснение
  провайдера; адаптеры 0x и Velora получили `error_detail` по образцу Uniswap.

1. **Production не стартует: `velora` включена без ссылки на учётные данные.**
   Сообщение: `configuration_invalid: ... provider velora is enabled in production
   without a credentials reference`, 13 попыток перезапуска 2026-09-10 07:18–07:20,
   после чего служба была остановлена и отключена.
   Причина подтверждена кодом и конфигурацией: `monik/config/root.py`,

## KyberSwap — пятый агрегатор (2026-09-13)

**Подтверждено живыми запросами** к `aggregator-api.kyberswap.com`:

- котировка приходит одним запросом `GET /{сеть}/api/v1/routes`; сеть
  указывается в пути, а не параметром;
- `routeSummary.amountOut` — сумма, которую получает владелец; партнёрская
  комиссия не задаётся, и `extraFee` приходит пустым;
- вместе с котировкой приходят расход газа (`gas`), цена газа в wei
  (`gasPrice`) и её оценка в долларах (`gasUsd`) — узел сети для этого
  провайдера спрашивать не нужно;
- ключ доступа не требуется; документация предписывает заголовок
  `x-client-id` с именем приложения, но запрос без него тоже отвечает `200`;
- отказы приходят числовыми кодами в теле при статусе `400`. Проверены
  живьём: `4011` (токен не найден), `4009` (сумма больше максимума), `4000`
  (некорректный запрос). Коды `4008` (маршрут не найден) и `4010` (нет
  подходящего пула) взяты из документации и живьём не наблюдались —
  KyberSwap находил маршрут даже для неликвидных пар;
- публичный лимит — 3 запроса в секунду, суточной квоты документация не
  называет.

**Проверено адаптером Monik:** `health_check` → `ready`; котировка 50 USDT →
4,435987 LINK с маршрутом `uniswap-v4+uniswapv3`; неизвестный токен →
`NoRouteError` категории `no_route`.

**Не подтверждено:** воспроизводимость маршрута для Level 2
(`supports_fixed_route = False`), поведение при суточных объёмах, реакция на
превышение 3 запросов в секунду.

**Измерение расхождения цен (2026-09-13):** разброс между KyberSwap и Velora
на паре USDT→LINK — 0,039 % на 50 USDT и 0,043 % на 1000 USDT. Круговой
убыток на тех же данных — 0,08–0,23 %, поэтому пятый агрегатор расширяет
перебор комбинаций, но сам по себе положительных возможностей не создаёт.
